# Domain 1 — General Security Concepts

This section documents my understanding and practical application of
CompTIA Security+ Domain 1: General Security Concepts.

The goal is not only to memorize security terminology, but to understand
how these concepts are applied in real-world security environments,
particularly from a SOC analyst perspective.

---

# 1.1 Security Controls & Categories

## Security Control Categories

Security controls can be categorized based on how they are implemented.

| Category | Description | Example |
|---|---|---|
| Technical | Implemented using technology | Firewall blocking malicious traffic |
| Managerial / Administrative | Policies, governance, and management decisions | Security policy requiring MFA |
| Operational | Human-driven security processes | Regular access reviews |
| Physical | Protects physical locations and assets | Mantrap at a datacenter entrance |

### Practical Example

A company wants to prevent unauthorized people from entering its
server room.

- A **badge reader** is a physical control.
- A **security policy requiring badges** is a managerial control.
- **Guards checking visitor access** is an operational control.
- A **system automatically denying an invalid badge** involves technical enforcement.

The category depends on **what implements the control**.

---

# Security Control Types

Controls can also be classified by their purpose.

| Type | Purpose | Example |
|---|---|---|
| Preventive | Stops an unwanted event | Firewall blocking malicious IP |
| Deterrent | Discourages an attacker | Security warning signs |
| Detective | Detects an event | IDS detecting suspicious traffic |
| Corrective | Restores or fixes after an event | Restoring a system from backup |
| Compensating | Alternative control when the preferred control cannot be used | Reverse proxy providing MFA for a legacy application |
| Directive | Tells people what they must/should do | Acceptable Use Policy |

### Practical Example

If a legacy application cannot support MFA directly, a reverse proxy
can be placed in front of it and enforce MFA.

The proxy acts as a **compensating control** because it provides
security functionality that the application itself cannot provide.

# 1.2 Fundamental Security Concepts

# CIA Triad

The CIA triad represents three fundamental security objectives:

## Confidentiality

Confidentiality means preventing unauthorized access or disclosure
of information.

### Example

An employee should not be able to view customer records unless their
job requires access.

Possible controls:

- RBAC
- Encryption
- Access control lists
- Authentication

---

## Integrity

Integrity means protecting data from unauthorized modification and
ensuring that information remains accurate and trustworthy.

### Example

An attacker compromises a web application and changes inventory
records from:

`100 units`

to:

`1000 units`

The system may still be running, but the data is now incorrect.

This is an **integrity violation**.

Possible controls:

- File Integrity Monitoring (FIM)
- Hashing
- Digital signatures
- Database auditing
- Access controls

---

## Availability

Availability means ensuring that systems and data are accessible
when authorized users need them.

### Example

A company's web server fails, but a redundant server automatically
takes over.

The service remains available.

Possible controls:

- Redundancy
- Failover systems
- Backups
- Load balancing
- Disaster recovery

---

# AAA Framework

AAA stands for:

- Authentication
- Authorization
- Accounting

## Authentication — "Who are you?"

Authentication verifies the identity of a user or system.

Examples:

- Username and password
- FIDO2 security key
- Fingerprint
- Smart card

---

## Authorization — "What are you allowed to do?"

Authorization determines what an authenticated identity is permitted
to access or perform.

### Example

An employee successfully logs into the billing system.

Authentication establishes:

> "This is the employee."

Authorization determines:

> "This employee can view billing records but cannot modify them."

Examples:

- RBAC
- File permissions
- Access control lists

---

## Accounting — "What did you do?"

Accounting records activity performed by users or systems.

Examples:

- Login events
- Files accessed
- Commands executed
- Configuration changes

These records are important for security monitoring and investigations.

---

# Non-Repudiation

Non-repudiation provides evidence that can help establish that a
particular identity performed an action or approved information.

### Example

A software release is digitally signed using a protected private key.

The deployment system verifies the signature using the corresponding
public key.

If the binary is modified after signing, signature verification fails.

Digital signatures can provide:

- Integrity
- Authentication of the signing key
- Evidence supporting non-repudiation

Important consideration:

Non-repudiation depends on proper protection of the private key and
properly establishing the identity associated with that key.

---

# Zero Trust

Zero Trust follows the principle:

> Never automatically trust a user or device simply because it is
> inside the network.

Access decisions should consider factors such as:

- User identity
- Device security
- Device compliance
- Location
- Risk
- Requested resource
- Context

## Implicit Trust Zones

An implicit trust zone exists when being inside a particular network
automatically provides access to resources.

### Example

If any device connected to the corporate LAN can automatically access
internal file shares, the network is implicitly trusting the device.

Zero Trust attempts to eliminate this assumption.

# Zero Trust Control Plane vs Data Plane

## Control Plane

The control plane makes and establishes access decisions.

### Policy Engine (PE)

The Policy Engine evaluates information and decides whether access
should be:

- Allowed
- Denied
- Revoked

### Policy Administrator (PA)

The Policy Administrator carries out or establishes the decision made
by the Policy Engine.

For example, it may establish:

- A short-lived credential
- A temporary access rule
- A dynamic firewall rule

### Simple model

```text
Policy Engine
     |
     |  ALLOW / DENY
     v
Policy Administrator
     |
     |  Establishes access
     v
Policy Enforcement Point
```

## Data Plane

The data plane handles the actual traffic or data.

### Policy Enforcement Point (PEP)

The PEP sits in the traffic path and enforces the access decision.

Simple rule:

```text
PE = Decides
PA = Establishes
PEP = Enforces
```

# Microsegmentation

Microsegmentation divides a network or environment into small
security boundaries and applies granular access rules.

### Example

A web server may only be allowed to communicate with the database
server it requires.

```text
             ┌──────────────┐
             │  Web Server  │
             └──────┬───────┘
                    │
                  ALLOW
                    │
                    ▼
             ┌──────────────┐
             │   Database   │
             └──────────────┘

Web Server ───────X──────► Admin Server
                  DENY
```

If the web server is compromised, microsegmentation can limit the
attacker's ability to move laterally through the environment.

# Deception Technologies

Deception technologies intentionally place fake resources or
information in an environment to attract and detect unauthorized
activity.

## Honeytoken

A fake piece of information that can alert defenders when used.

Example:

```text
AWS_ACCESS_KEY = FAKE_KEY
```

If someone attempts to use the fake credential, the security team
can investigate.

**Fake data/credential → Honeytoken**

---

## Honeyfile

A fake file designed to attract an attacker or detect unauthorized
access.

Example:

```text
HR/
└── Executive_Salaries.xlsx
```

The file contains fake information and generates an alert if accessed.

**Fake file → Honeyfile**

---

## Honeypot

A fake computer or server designed to attract attackers and observe
their behavior.

Example:

```text
Internet
    |
    v
Fake Apache Web Server
    |
    ├── Fake customer records
    ├── Fake transaction logs
    └── Deliberately vulnerable software
```

The system has no production value and exists primarily for
detection and observation.

**Fake system/server → Honeypot**

---

## Honeynet

A collection of interconnected deceptive systems that creates a
larger fake environment.

Example:

```text
             Fake Network
                  |
       ┌──────────┼──────────┐
       ▼          ▼          ▼
   Fake AD     Fake Web    Fake DB
   Server      Server      Server
```

**Fake network/environment → Honeynet**

# Practical Security Perspective

The concepts in this domain are not isolated definitions.

In a SOC environment, they can be used to understand and investigate
security events.

For example:

```text
Security Event
      |
      v
What happened?
      |
      ├── Unauthorized disclosure?
      |       → Confidentiality
      |
      ├── Unauthorized modification?
      |       → Integrity
      |
      └── Service unavailable?
              → Availability
```

A SOC analyst can then determine:

1. What security objective was affected?
2. Which control should have prevented or detected it?
3. Which security control category applies?
4. What evidence exists in the logs?
5. What corrective action should be taken?

This is the approach I am using to connect Security+ theory with
practical SOC analysis.
