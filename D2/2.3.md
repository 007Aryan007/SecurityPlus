# CompTIA Security+ 2.3 Vulnerabilities

## 1. Application & Web Vulnerabilities

### Memory Leaks
* **Definition:** An application allocates memory (RAM) but fails to release it back to the OS when finished.
* **Threat:** Exhausts system resources, leading to a **Denial of Service (DoS)** or system crash.
* **Mitigation:** Secure coding practices; using memory-managed languages (like Python or Java) that feature **Garbage Collection** (automatic memory cleanup).

### Buffer Overflows
* **Definition:** A program puts more data into a memory buffer than it was designed to hold, spilling over into adjacent memory.
* **Threat:** **Remote Code Execution (RCE)**. Attackers overwrite legitimate memory pointers to execute their own malicious instructions.
* **Mitigations:**
  * **Bounds Checking:** Input validation in the code to limit data length.
  * **DEP (Data Execution Prevention):** OS-level protection that marks data sections (like the stack) as non-executable (NX bit). Stops attackers from running code injected into data fields.
  * **ASLR (Address Space Layout Randomization):** Shuffles memory addresses every time an app runs, making it nearly impossible for attackers to reliably point the CPU to specific system functions.

### Race Conditions (TOCTOU)
* **Definition:** When a system attempts concurrent operations, but the sequence gets jumbled. Common form is **Time-of-Check to Time-of-Use (TOCTOU)**.
* **Threat:** Attackers exploit the tiny window of time between when a system *checks* a condition and *acts* on it (e.g., duplicate bank withdrawals).
* **Mitigations:**
  * **Mutexes:** Software locks that force concurrent requests to wait in a single-file line.
  * **Atomic Operations:** Combining the check and the action into a single, uninterruptible database transaction.

### SQL Injection (SQLi)
* **Definition:** Injecting malicious SQL commands into user input fields (like `' OR 1=1 --`) that the backend executes against the database.
* **Threat:** Bypassing authentication, stealing database tables, or deleting data.
* **Mitigations:**
  * **Parameterized Queries (Prepared Statements):** The ultimate fix. Sends the SQL command structure and user input separately, forcing the database to treat input strictly as literal data, never as executable code.
  * **Web Application Firewall (WAF):** Blocks known SQLi signatures at the network edge.

### Cross-Site Scripting (XSS)
* **Definition:** Injecting malicious client-side scripts (usually JavaScript) into a web application. **Targets the user's browser**, not the server.
* **Types:**
  * **Stored (Persistent):** Script is saved to the database (e.g., a forum comment) and executes when *any* user visits the page.
  * **Reflected:** Script is embedded in a malicious link (e.g., phishing email), bounces off the server, and executes only when the victim clicks it.
* **Threat:** Session hijacking (stealing cookies), redirecting users.
* **Mitigations:** **Output Encoding** (converting `<script>` to safe text like `&lt;script&gt;`) and strict input validation.

### CSRF (Cross-Site Request Forgery)
* **Definition:** Tricking a user's browser into executing an unwanted action on a site where they are currently logged in. Exploits the browser's automatic sending of session cookies.
* **Threat:** Unauthorized actions on the user's behalf (e.g., transferring funds).
* **Mitigations:** 
  * **Anti-CSRF Tokens:** Hidden, single-use secret tokens embedded in web forms.
  * **SameSite Cookie Attribute:** Tells the browser never to send the session cookie on cross-site background requests.

## 2. System & Infrastructure Vulnerabilities

### Unpatched Systems
* **Definition:** Systems missing vendor-supplied security updates for known flaws (CVEs).
* **Threat:** Exploitation of known vulnerabilities (or Zero-Days) leading to ransomware or system compromise.
* **Mitigation:** Strict **Patch Management** (testing updates in a sandbox, then deploying them across the enterprise environment).

### End-of-Life (EOL) / Unsupported Products
* **Definition:** Software or hardware that the vendor no longer supports or provides security patches for (e.g., Windows 7).
* **Threat:** Any newly discovered vulnerabilities will remain unpatched forever.
* **Mitigation:** Upgrade the system. If impossible (e.g., legacy hospital equipment), use **Compensating Controls** like network isolation or air-gapping.

### Misconfigurations
* **Definition:** Fully patched systems configured insecurely by human error (e.g., leaving debug mode on, backward firewall rules).
* **Threat:** Gives attackers an open door without needing complex exploits.
* **Mitigation:** **System Hardening** (disabling unnecessary features) and enforcing **Secure Baselines** (standardized security templates like CIS Benchmarks).

### Default Credentials
* **Definition:** Factory-set usernames and passwords (e.g., admin/admin) left unchanged on network devices, especially **IoT** hardware.
* **Threat:** Attackers can easily look up the manual and walk right in (e.g., Mirai Botnet).
* **Mitigation:** Change passwords immediately upon deployment and disable default "admin" accounts.

## 3. Virtualization & Cloud Vulnerabilities

### Misconfigured Cloud Buckets
* **Definition:** Cloud storage folders (like AWS S3) accidentally set to "Public" instead of "Private".
* **Threat:** Massive data breaches; attackers can download files directly via a web browser without authentication.
* **Mitigation:** Strict **IAM (Identity and Access Management)** rules and automated **Cloud Security Posture Management (CSPM)** tools to monitor permissions.

### Container Breakout
* **Definition:** An attacker hacks an isolated container (like Docker) and exploits a flaw to escape onto the underlying host server's OS.
* **Threat:** Total compromise of the host server and all other containers running on it.
* **Mitigation:** Never run containers in **Privileged Mode** (which gives root access to the host). Enforce the Principle of Least Privilege and keep the container engine/host OS patched.

### Weak API Permissions
* **Definition:** Assigning overly broad "Admin" rights to API keys/tokens that only need limited access.
* **Threat:** If an API key is leaked (e.g., hardcoded on a public GitHub repo), attackers gain massive control over the cloud environment.
* **Mitigation:** 
  * **Principle of Least Privilege:** Scope keys specifically to their required task.
  * **OAuth / Access Delegation:** Use secure authentication protocols that utilize temporary, rotating **Access Tokens** and long-lived **Refresh Tokens** instead of permanent, static passwords.
